# Данные и предметные правила

## Два независимых хранилища

`BaseIFace` открывает PyMySQL-соединение при входе в `with` и закрывает при выходе. Настройки берутся из `current_app`, поэтому требуется контекст Flask. Основные чтения используют `DictCursor`. SQL хранится преимущественно в `Queries`, часть запросов встроена в `db.py`.

Ниже — объекты, установленные по SQL-запросам, а не полная схема БД. Без DDL нельзя надёжно утверждать типы всех столбцов, индексы, внешние ключи или то, какие объекты являются таблицами, а какие представлениями.

| Группа | Объекты MySQL | Назначение |
| --- | --- | --- |
| Игроки | `players`, `cities`, `questionaries`, `students`, `external_ids` | Основные данные, города, анкеты, учащиеся, внешние идентификаторы |
| Рейтинги | `rate_history`, `ratelist`, `rate_forecast`, `razr_change`, `mb_stat` | История, текущая классификация, прогноз, изменения разрядов, статистика баллов |
| Результаты | `results`, `results_ses` | Начисления и результаты, в том числе сессии |
| Турниры | `tourn_header`, `tourn_site_data`, `streams`, `families` | Заголовки, данные сайта, серии и семьи |
| Участники | `tourn_ind`, `tourn_pair`, `tourn_ses`, `tourn_team` | Индивидуальные, парные, сессионные и командные записи |
| Команды | `teams`, `team_players`, `team_players_nonqual` | Команды, составы и участники вне зачёта |
| Прочее | `admin_pos`, `tds`, `events`, `events_part`, `clubs` | Должности, судейство, события, клубы |
| Новые ID | `fsbr_aux.new_players` | Заявки на новых игроков в отдельной схеме |

Историческое именование важно: `players.firstname` в текущем преобразовании соответствует фамилии (`Player.lastname`), `players.lastname` — имени (`Player.firstname`), `surname` — отчеству. При доработках нельзя механически сопоставлять названия полей.

## Пользователи SQLAlchemy

| Таблица | Поля / связи |
| --- | --- |
| `users` | `id`, `facebook_id`, `google_id`, `twitter_id`, `nickname`, `email`, `fsbr`; связь с ролями |
| `roles` | `id`, уникальное `name`, `description` |
| `user_roles` | `user_id` → `users.id`, `role_id` → `roles.id` |
| `flags` | Строковый первичный ключ `flag`, булево `value` |

`User.fsbr` — идентификатор автора для регистрации нового игрока, без объявленного внешнего ключа в MySQL. Новый пользователь находится или создаётся по идентификатору провайдера. Автоматического объединения пользователей по email нет. Роль `Admin` разрешает менять блокировку; `AddPlayers` проверяется в шаблонах. Если флаг `locked` отсутствует, база считается разблокированной.

## Даты, разряды и баллы

- `Helper.getDate` сортирует доступные даты: выбирает ближайшую снизу, а до начала истории — минимальную. Пустой список не обработан.
- `Helper.getRazr`: при значении БД больше 50 вычитает 100 и помечает разряд временным. Для получившегося значения 30 возвращает `1.2`, если коэффициент отсутствует, иначе `coeff * 0.3`; прочие значения делит на 2. Результат округляется до одного знака. В строковом представлении временный разряд получает `*`.
- В HTML-списках клубов и учащихся `rmb = mb + emb`; если `mb < 2 * emb`, используется `round(float(mb) * 1.5 - 0.01)`. Это описание реализации, не формулировка действующего регламента федерации.
- XLS содержит ID, ФИО, город, разряд, МБ (`mb + emb`), ПБ, рейтинг, признак временного разряда, клуб, категории, наличие анкеты и email. Содержимое выгрузки следует учитывать при определении политики доступа.
- При чтении внешних ID сохранённый ненулевой `wbf_id` увеличивается на 20000 перед помещением в объект игрока.

## Типы турниров

| Код | Имя XML / загрузка |
| --- | --- |
| 1 | `Individual`, индивидуальные участники |
| 2 | `Pair`, пары |
| 3 | `Team`, команды |
| 4 | `Session`, индивидуальная или парная запись определяется составом |
| 5 | `Club`, индивидуальный загрузчик |
| 6 | `Festival`, отдельный загрузчик участников в сервисе не вызывается |

Родительские связи читаются через `tourn_header.parent`, формируют предков и вложенные турниры. Объект `Tournament` также хранит навигацию `prev` / `next` и семью.

## Регистрация ID

`addNewPlayer` получает исходный номер из запроса `select_max_id`, затем увеличивает его и проверяет отсутствие в `players` и `fsbr_aux.new_players`. После этого делает параметризованный INSERT и `commit`. Запрос исходного номера использует `limit 1, 1` для `players`, то есть вторую строку по убыванию, а не буквально максимальную. Дальнейшая проверка занятости снижает риск повторения номера, но не обеспечивает атомарное распределение при параллельных запросах; гарантии зависят также от ограничений БД, не представленных в проекте.
